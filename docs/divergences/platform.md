# Divergences — Platform area (Dashboard, Settings, Team, Feature requests, Backlinks)

| Area / screen | Designed behavior | What was built instead | Why | User-visible? | Status |
|---|---|---|---|---|---|
| App shell → account | — (the design has no sign-out affordance anywhere) | Nothing added. `POST /api/auth/signout` exists, but there is no UI to reach it. | The design omits it; adding UI needs approval (README §2.1). Users currently can't sign out. | Yes | Needs approval |
| Dashboard → PerfSummary (connected) | Metrics from canned series, with a Sample badge | Real `gsc.summary {days:28}`. While it loads, the three values show skeleton bars. When nothing has synced yet (summary is null), the values show "—" and no sparkline. No Sample badge. The Clicks delta is hidden when there's no previous 28-day window. | The loading and no-data states aren't designed; "not collected" must never read as zero (principle #4). | Yes (loading/no-data only) | Needs approval |
| Dashboard → Needs attention → GSC error | "Google returned a temporary error. Data up to Oct 13 is safe." | Uses `B.gsc.lastSyncedThrough` (as "Mon D"). If nothing was ever synced, only the first sentence shows. | No date to quote when no data was synced. | Rare | Needs approval |
| Dashboard → Needs attention → failed publish | "… rejected the request (401)." | Uses `entry.publishError.http` and `publishError.platform`, falling back to the entry's destination connection's platform. If no HTTP status is recorded, the "(…)" part is omitted. | Real errors may have no HTTP status (e.g. a network timeout). | Rare | Needs approval |
| Dashboard → "{n} high-priority suggestions" | Fixed head "Two pages are close to page one." and body "Refreshing “Scope creep” could add 80–140 clicks a month." | Built from the user's real top open High suggestion (`suggestions.list`), following the same pattern. Refresh: "{N} page(s) is/are close to page one." + "Refreshing “{subject}” could add {range} clicks a month." Meta: "{N} page(s) could earn more clicks from the same rankings." + "Rewriting the title on {path} could add …". Other kinds: "{N} high-priority improvement(s) are ready." When the impact isn't a click estimate, the body is the suggestion title. The issue is omitted when suggestions can't be loaded. Shown when `B.counts.highSuggestions > 0` (not only when GSC is connected and a calendar exists). | Principle #6: every claim comes from the user's own data. | Yes (wording varies with data) | Needs approval |
| Settings → Publishing → Schedule | Timezone select with 4 zones | Native select with the full IANA list; the prototype's 4 zones lead it. A native select supports type-to-find, so it isn't a custom searchable combobox. **Closes known risk #8** for Settings. | 02-system §15 asks for the full IANA list. | Yes | Needs approval |
| Settings → Calendar defaults | Market select lists `MARKETS` | If the business's current market or language (from its profile) isn't in the list, it's added at the top so the select shows the true value. | Otherwise the select would show the wrong market. | Rare | Logged |
| Settings → AI models | Model catalogue | Labels, ids and descriptions are exactly as in `radar-models.jsx`. Provider API ids are mapped in `src/server/ai` (core). **Known risk #4** belongs to the core AI layer; nothing in this area changes labels. | — | No | Logged |
| Settings → permissions | — | Server-side enforcement (02-system §14). AI models, Team, joining/leaving the backlinks network and backlink preferences need Admin or above. Calendar defaults and backlink approve/decline/re-check/removal need Editor or above. Feature requests: any member. Viewers see the same Settings UI, and their changes are rejected with "You don’t have permission to do that." | The design has no role-specific UI, so we show the same UI and enforce on the server. | Yes (error toast for lower roles) | Needs approval |
| Team → invite acceptance | "Invites go out by email with a signed link." | Token = random + HMAC (only its sha256 is stored). Single use, expires after 14 days. **Policy: any signed-in user holding a valid link joins with the invited role, even if their account email differs.** The member row then takes the account's email, and the inviter sees it change. | People are often invited at a work alias and sign in with another address. The link is the credential, like most team-invite systems. Stricter alternative: require an email match. | Yes | Needs approval |
| Team → invite link while signed out | — | Redirects to `/signup?next=/api/invites/{token}`. **Depends on the onboarding/auth area:** the Signup/Sign-in screens must redirect to `next` after success. Right now `/signup` redirects signed-in users to `/dashboard` and ignores `next`, so a new user must open the link again after signing up (it then works). Sign-up already links pending invites for that email (`attachInvites`). | Signup/signin pages belong to another area. | Yes | Needs approval (cross-area) |
| Team → invalid or expired invite link | Not designed | Signed in: redirect to `/dashboard`. Signed out: redirect to `/signin`. No message is shown. | No copy is designed for a dead link. | Yes | Needs approval |
| Team → remove member | "Revokes access immediately" | The member row is deleted, and every API request re-checks membership. An already-open live-events stream (SSE) for that user ends within its 4-minute cycle, but it carries no data beyond revision pings and toasts. | Implementation detail. | No | Logged |
| Team → invite email failure | — | If the invite email can't be sent, the pending row is removed and the user sees "Radar couldn’t send the invite. Try again." | Avoids "Invited" rows nobody received. | Rare | Needs approval |
| Request a feature | Toast only | Stored in `feature_requests` and emailed to `SUPPORT_INBOX`. If that isn't configured, the request is stored and a warning is logged. Dev stubs send to the outbox log. | — | No | Logged |
| Backlinks → join toast | "Welcome to the network. Radar found 3 relevant matches." | The real count from the first matching run. The Join button spins until matching finishes (up to 60s) and singularizes "1 relevant match". If matching hasn't finished by then: "Welcome to the network. Radar is looking for relevant matches." | The count is computed for real. The fallback copy isn't designed. | Yes | Needs approval |
| Backlinks → network model | Partner proposals | A placement is a pair. The business whose page would carry the link gets "Links from you" (only if it accepts requests, `prefs.outbound`). The business that would receive the link gets "Links to you". An outbound link is inserted on publish only when both sides approved. | "You approve every link … on your site, or pointing to it" (principle #10). | No | Logged |
| Backlinks → matching rules | Weekly, up to `prefs.max` per month | Weekly cron (business timezone, Monday-keyed), plus one run right after joining. The monthly cap counts inbound and outbound together. Each run saves room for one outbound request when outbound is on. At most one proposal per partner per direction every 60 days. Partners must share a language and not be competitors (either side's list, when that side has `excludeCompetitors`). Relevance = token overlap of topics, offerings, needs and audience. The LLM can still return "no genuine fit". Drafts must keep ≥60% of the host's sentence and must not use an exact-match commercial anchor (checked on the server). | Implementation detail of §13. | No | Logged |
| Backlinks → rel | `rel="sponsored"` when Qualify is on, else the partner's choice; "Editorial" when placed independently | `rel="sponsored"` when either side has Qualify on. If both turned it off: `rel="nofollow"`. Links discovered on partners' pages that weren't placed through a proposal are recorded as "Editorial". | Defines "partner's choice" concretely while keeping network links qualified. | Yes (rel text) | Needs approval |
| Backlinks → disclosure text | Examples in fixtures | "Inline disclosure: “Partner link”" when the host publishes through Radar (Radar inserts "(Partner link)" after the anchor). Otherwise "Placed through the Radar network, noted on their partner page". | — | Yes (copy) | Needs approval |
| Backlinks → Undo | Undo in the toast | Decisions take effect immediately, but partner emails go out 20s later and are skipped if undone. Undo restores the previous state (pending or "Auto-approved by your rules"). | Undo must not leave a sent email behind. | No | Logged |
| Backlinks → decline | "An optional note is sent to the partner" | The partner is emailed only when a note is added. | Avoids notifying partners about proposals they never saw. | No | Logged |
| Backlinks → auto-approve | Computed live from prefs in the prototype | Applied when a proposal is created, and to pending proposals when preferences are saved. | Backlinks → proposal list | Decided cards stay in the list | Approved placements leave "Links to you / Links from you" once the crawler confirms them live; they show in Live links instead. | Otherwise "Approved · awaiting placement" would stay on a live link. | Yes | Needs approval |
| Backlinks → Re-check result | Only "Re-checked. Still missing — the partner has been notified." | Adds "Re-checked. The link is live again." when the link is found. | A real check can succeed. | Yes (new toast copy) | Needs approval |

An unreachable page leaves the status unchanged. | "Right rel" requirement; avoids false "lost" on transient errors. | No | Logged |
| Backlinks → leave | Stops new proposals; links remain | Also withdraws undecided proposals on both sides. Decided ones and live links stay. | — | No | Logged |
