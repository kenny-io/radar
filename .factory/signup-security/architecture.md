## Current abuse-control decision (supersedes initial mandatory-Turnstile design)

The user explicitly authorized IP/rate-limit protection when existing Turnstile hostname configuration could not be established: “if you can't figure it out, leave turnstile and protect via IP, or rate limiting the sign ups”. The active/default design is therefore rate-limit mode, with optional Turnstile only after explicit verified activation. Email ownership confirmation, Google identity isolation and legacy credential/session migration remain mandatory.

`RADAR_SIGNUP_TURNSTILE=1` is the sole opt-in. An unset variable or any other value selects rate-limit mode. Possession of the recovered site/secret keys alone must not enable it. Enabled mode fails closed on missing keys, unapproved public test keys in production, invalid challenge, hostname/action mismatch or provider failure; there is no automatic fallback. Default rate-limit mode does not render or require a challenge and does not call Cloudflare. Production mail configuration is mandatory in both modes.

This is an explicit product/security tradeoff, not a claim that IP throttles identify people: distributed IPs can consume the fixed global budget, and a targeted attacker can use the per-address quota to delay confirmation delivery. The shared global budget bounds unauthenticated pending-account creation and confirmation mail volume; mailbox proof still prevents account access. Record and monitor budget hits using existing safe logs. No additional infrastructure is introduced.

## Decisions

1. Email ownership is required before any non-guest authenticated access. Existing password accounts are not silently grandfathered as verified.
2. Signup asks for name and email; the mailbox holder chooses a password on the confirmation page. Do not preserve a password supplied by an unverified registrant and activate it when another person clicks an email. This prevents pre-registration attacks rather than merely postponing them.
3. Google identities are looked up by Google `sub`; matching email alone never links an existing account. New Google users can register only when email/sub unique constraints permit. Existing password users receive sign-in/recovery guidance on collision. Adding a new explicit authenticated provider-linking product flow is outside this bounded fix; automatic email-only linking is removed.
4. Previous Google `googleSub` is evidence of prior verified Google authentication in this implementation, but a legacy mixed password could have been attacker-selected. Migration preserves the Google identity, clears every legacy Google account's password hash, and revokes all non-guest sessions. Existing Google users sign in with Google again. Their old password intentionally no longer works.
5. Businesses, ownership/memberships, complimentary access, billing rows, subscriptions, publishing credentials and background jobs remain intact. Guest rows/sessions remain intact. Existing password users recover by requesting a confirmation email without needing the old password, then choose a new password; they regain the same user ID and records.

## Data and trust boundaries

`users.emailVerifiedAt`: nullable timestamptz, default null. Guests remain null and keep their separate `radar_guest` capability. SessionUser's external shape need not expose the timestamp. `currentUser()` must filter non-guest AND non-null `emailVerifiedAt`; all privileged endpoints, admin metrics, invite attachment and business access inherit this trusted principal. Also guard session creation/finishAuth against unverified users so future call sites cannot issue usable sessions accidentally.

`emailVerificationTokens`: `tokenHash` text PK; `userId` UUID FK users cascade; canonical `email` text; `expiresAt` timestamptz; safe relative `next` text nullable; `createdAt`. Index expiry and user for cleanup/revocation. Generate 32 cryptographically random bytes, persist SHA-256 only, expire in 30 minutes. A token grants the mailbox holder the narrow ability to verify one unverified identity and choose its password. Do not include user-selected URLs, account names or arbitrary HTML in the security message.

A migration adds the column/table, sets `email_verified_at` for existing non-guest users with a Google subject, clears their password hashes, and deletes all non-guest sessions. No password-only user is marked verified. Migration is one-way for credential revocation: never restore unsafe passwords or session tokens from a rollback.

## HTTP contracts

All mutations retain same-origin checks and streamed 8KB bodies. Zod strings are bounded. Use existing safeNext to normalize stored redirects; no protocol-relative/backslash/control-character redirects. Responses are no-store. Security email pages are noindex and no-referrer.

- `POST /api/auth/signup {name,email,turnstileToken?,next?}`: validate input, route and combined shared IP limits, optional explicitly enabled bot gate, shared mail budgets and production provider availability before account existence branches. Return `200 {ok:true,verificationRequired:true}` generically for valid addresses regardless of existence. New address: insert pending user with null password/no session, send confirmation. Existing unverified address: send confirmation without changing name/password/ownership. Existing verified address: no account mutation or token creation; generic response remains identical. Never attach invites, claim guest drafts or issue session here. Unique-email races re-read current state; never overwrite an existing user.
- `POST /api/auth/verification/resend {email,turnstileToken?,next?}`: same generic response, origin/body/shared IP/optional bot/config boundaries; send only for existing unverified non-guest users. Unknown/verified/guest email gets the same success response and no token. Password is not required. The UI also exposes this entry path from sign-in for legacy recovery.
- `GET /verify-email`: render a page, never activate or consume a token. Link is `/verify-email#token=<opaque>`. The client reads and immediately removes the fragment with history.replaceState, keeps token in memory, asks for a new password, and submits to the endpoint below. Mail scanners and refreshes cannot silently activate accounts; refresh after fragment removal offers resend.
- `POST /api/auth/verify-email {token,password}`: shared IP limit, bounded token/password, 8 minimum characters and at most 72 UTF-8 bytes. Hash the proposed password before the short transaction. Lock the relevant user row, atomically consume an unexpired token whose canonical email still matches an unverified non-guest user, set verified timestamp/new password, delete all other verification tokens and all sessions for that user. Exactly one concurrent consume succeeds. Already verified, missing, expired, reused or wrong-email tokens return the same `400 verification_invalid` with resend guidance. No token value in error logging. Commit first, then attach invites and finishAuth to claim this browser's guest, create a new session and return `{ok:true,next}`. If post-commit session creation fails, the verified account remains recoverable with its new password. Do not claim another browser's guest.
- `POST /api/auth/signin`: verified password users retain normal behavior and limits. A valid password for an unverified legacy user returns a verification-required response and may invoke the same budgeted confirmation helper; no session, draft claim or invite attachment. Users who do not know the old password use the separate resend UI. Google-only users see guidance to use Google in the recovery/sign-in copy; do not expose a way to retain/restore the revoked legacy password.

Use `{ok:true,verificationRequired:true}` as an additional AuthResult variant alongside `{ok:true,next:string}`. Shared engineer owns this type. Frontend handles the discriminant before redirecting.

## Google callback

Continue consuming a browser-bound, single-use 10-minute state before processing identity. Use `jose`'s existing dependency to validate issuer/audience/expiry/signature against Google's JWKS rather than decode-only validation. Require `email_verified === true`, bounded valid `sub`, canonical valid email, and never accept guest-domain addresses. Google token endpoint call remains TLS with timeout; signing keys use jose remote JWKS caching.

Lookup `googleSub` only. Existing subject must be verified; sign in with its stored email and user ID, not a changed provider email, preserving canonical account identity and avoiding invite attachment under unowned addresses. New subject + unused email inserts a verified Google-only account with no password. New subject + occupied email refuses linking and redirects `/signin?error=google_link`; copy explains using existing email sign-in or confirming/recovering the account. Race: insert conflict must re-read by sub; permit only exact subject match, never fall back to email. A differing subject for an existing email is never reassigned. Retain safe stored next and guest-claim behavior only after verified authentication.

The development identity stub remains impossible in production. Signature-invalid, expired, wrong issuer/audience and unverified Google responses must be tested with a mocked trusted endpoint/JWKS, separately from the identity stub.

## Bot and delivery controls

Keep the existing guest `verifyHuman` seam separate, avoiding an unrelated guest-onboarding break until that page has a widget. Signup/resend operate in rate-limit mode by default. Server pages pass an explicit `turnstileRequired` boolean from `env.signupTurnstileRequired`, derived solely from `RADAR_SIGNUP_TURNSTILE === '1'`, alongside the runtime site key and development-stub status. The secret never enters client props. With the flag off, the UI renders no widget/loading state and permits submission without a token; the backend skips Cloudflare while retaining every rate and email-ownership boundary.

With the flag on, require both `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` outside explicit nonproduction stubs; missing configuration fails closed with generic `503 auth_unavailable` before email/account existence branches. Public test credentials cannot be production bot protection. Explicitly render a managed widget with action `turnstile-spin-v2`; require its token on signup/resend, clear token on expiry/error and reset widget after every server attempt (tokens are single use). Script/network failure exposes accessible retry/status without approval fallback. Google sign-in does not depend on this optional password-signup widget.

Enabled-mode backend posts token and remote IP to Cloudflare Siteverify with a finite timeout; require HTTP success, parsed `success === true`, expected action and hostname equal to configured APP_URL hostname. Missing/invalid/replayed/expired tokens, malformed payloads and network/provider failures never insert users/send mail. Production missing Resend credentials fails closed in both modes before looking up the account, with a generic unavailable error and no credential details.

Retain existing route limits: signup 10/IP/hour, resend 10/IP/hour, signin 30/IP/15min plus 10/account/15min. Add one shared security-mail IP key `auth:verification:shared-ip:<trustedIP>` limited to 10/hour across BOTH signup and resend so alternating endpoints cannot double the mail/pending-account budget. Both route and combined IP limits run before optional challenge verification. In enabled mode, validate Turnstile next; failed challenges must not consume someone else's per-email or global mail quota. In rate-limit mode, proceed directly to those mail budgets. In both modes, consume 3/canonical-email/hour and 300 globally/hour before account insertion or delivery; use hashed email keys and count attempts consistently regardless of account existence. This bounds pending rows and send volume even when addresses/IPs rotate. Verification-token consumes retain their separate IP limit before bcrypt work. Fixed windows can permit boundary bursts; validate Railway trusted proxy hops for the actual ingress. These are shared PostgreSQL counters, not per-process memory limits.

Do not pass token-bearing mail through current plaintext outbox/console behavior. Add a narrowly scoped sendAuthMail helper alongside existing sendMail: production outbox stores only recipient/subject/status plus a redacted placeholder, never token-bearing text/HTML/provider body errors; provider receives the actual message over TLS with timeout. PM approved local capture only when env.devStubs is true (which is impossible in production): store `encrypted-auth:` followed by encrypt({text,html}) in outbox.text using existing encrypt/decrypt, with html null. No console body output. QA may decrypt in a local fixture script; no app endpoint exposes capture data. All production auth outbox bodies remain redacted. Explicit stubs can suppress actual delivery, but production missing provider cannot silently report mail as delivered. Provider failures delete only the undelivered token hash, preserve older valid links, keep account unverified and permit rate-limited retry. Return the same safe provider failure for valid addresses before branching where practical; do not log full Resend response bodies that may contain message data.

## Validation gates

- Pending signup cannot read protected app/admin, claim guests, attach invites or create session. Default rate-limit mode renders no widget and accepts no-token submissions only within route+combined-IP/address/global budgets; alternating signup/resend cannot exceed shared IP budget. Enabled Turnstile mode rejects missing/bad/expired/replayed challenges, wrong action/hostname and upstream failures before user/mail creation or email/global-budget consumption. Production mail configuration is required in both modes; enabled-mode bot configuration is additionally required. Known and unknown valid addresses get equivalent configuration failures.
- Mailbox holder sets password on confirmation; initial registrant's chosen password never activates. Consume is single-use/expiring/race-safe; old tokens revoked; old sessions revoked; invalid tokens do not alter user.
- Migration fixture covers password-only, Google-only, mixed, guest and paid/complimentary accounts; row IDs, memberships/businesses/billing records preserved; all non-guest sessions revoked; password-only unverified; Google verified and legacy mixed password cleared.
- Legacy no-password recovery path works; duplicate/resend unknown/verified responses generic; email/IP/global budgets apply before costly/send work; delivery outage does not activate account and retry works.
- Google email collision including the prior attack never merges; valid same subject signs in; altered subject/wrong signature/issuer/audience/expiry/unverified claims rejected; state is browser-bound/single-use; unique insert race cannot fall back to email.
- Ordinary verified signin, Google return, safe invite next, same-browser guest draft claim and billing gate remain correct; unverified admin-allowlist claim stays denied.
- Browser desktop/mobile, keyboard labels/status/errors, slow hydration, widget expiry/retry, confirmation refresh, mail scanner GET and route recovery. Full tests/typecheck/build after integration, with baseline exceptions recorded.

## Rollout and rollback

No merge or deployment authorized by this task alone. A later production release can use default rate-limit mode with `RADAR_SIGNUP_TURNSTILE` unset or off; confirm the shared PostgreSQL quotas, actual proxy IP trust and real sender/domain deliverability with existing Resend configuration. Recovered Thally keys are optional and remain private. Before explicitly setting `RADAR_SIGNUP_TURNSTILE=1`, first confirm the existing widget permits the production hostname and complete a real hostname/action-validated challenge, then set runtime site/secret keys. Do not ship production public test keys or secret bypasses. Existing Google users are told to sign in with Google; password users are told to confirm email and choose their password once. No bulk unsolicited migration mail is needed.

The web service runs migrations in preDeployCommand before replacing the old process. This additive schema alone does not stop the old binary from issuing unverified sessions during overlap. A release must therefore stop/drain old web traffic while applying the credential-reset migration and starting the new revision, or run a final guarded non-guest session revoke after the last old process is gone. Keep an explicit short auth maintenance window if platform atomic traffic switching cannot guarantee this. Do not mark rollout complete from variable-store readback alone: confirm actual running containers, schema and signed-in gates. Worker billing/publishing continuity does not depend on email verification and should remain unchanged.

Rollback must retain the hardened authentication boundary; deploying the old signup/session code reopens vulnerabilities and is not an acceptable recovery. Prefer a forward fix or maintenance mode; keep additive schema and preserve credential revocations. Never restore old session/password snapshots. Private production backup is for recovery of other data, not re-enabling compromised credentials. Check aggregate counts and ordinary-user core flows after deployment; avoid outputting addresses/token URLs.

Reviewed integrated implementation on branch `kenny/signup-security`, base `f9eb6178`, 4 November 2026 (Asia/Dubai). This pass inspected application code, route/UI integration, existing-account migration, auth mail handling and behavioral test source independently from the implementation engineer. It did not repeat QA's browser runs or claim developer test results as independent execution. Security-source fingerprint SHA-256: `3c67fb30523f009ee6e2bfd9dc896ead8a880ab48545f3c513cc1fbb3118cd22` (ordered path plus content hashes of the 21 security implementation/migration/UI files reviewed; excludes tests and planning records).

All three originally reproduced exploit paths are closed in the reviewed source:

- Signup does not accept a password as a credential, issue a session, attach invitations or claim guests. Confirmation gives the inbox holder password choice. `currentUser`, `createSession` and `finishAuth` each enforce a verified non-guest identity, covering privileged APIs/admin and guest claims.
- Confirmation checks token hash/expiry, user email binding and unverified/non-Google status, locks the user, consumes once, replaces password and revokes all sibling tokens/sessions in one transaction. Concurrent use of the same or distinct links cannot activate twice because they serialize on the identity lock. Token-bearing links use fragments and explicit POST, not GET activation. Production outbox/errors do not retain raw security links.
- Google authentication verifies RS256/JWKS, issuer/audience/expiry and verified email; resolution and conflict fallback use Google subject only. Email-only collisions never grant access or retain the pre-registrant's credential. Existing Google subjects use the stored identity/email, preserving canonical account ownership/invites.
- Migration marks only historical Google identities verified, clears their legacy passwords and revokes all non-guest sessions. Password-only identities remain unverified until inbox recovery sets a fresh password. Users/businesses/memberships/billing are not deleted. Guest sessions remain separate.
- Signup/resend bot validation checks strict success, exact action and hostname, HTTP success and timeout; absent config/test keys/production bypass fail closed. New guest-specific key keeps this rollout from silently enabling the unfinished guest widget.

The review identified one medium availability defect: per-email/global confirmation budgets were consumed before validating Turnstile. A caller without a solved challenge could exhaust the victim's three-email quota or the global budget. Engineer applied the recommended order; final readback confirms configuration/IP protection, then a valid Turnstile challenge, then mail budgets before insertion/delivery. QA must retain the failed-challenge/no-mail-budget-consumption regression.

No remaining high-confidence authentication bypass, credential-retention flaw, token-consumption race or migration data-loss defect was identified in the reviewed source. Release readiness still depends on independent integrated QA/build/typecheck and the external gates below.

Nonblocking metric issue: confirmation tracks `user.signed_up` even for a legacy account whose original signup was already recorded. That can overcount founders; it does not create duplicate users, grant access or weaken recovery. A separate confirmation/recovery event or deduplicated signup metric is a future reporting correction, not an authentication blocker.

## A4 user-authorized rate-limit mode contract review

After A3, the user chose IP/rate-limit signup protection instead of waiting on Turnstile configuration. The earlier A3 implementation fingerprint/sign-off remains a historical review of the mandatory-challenge version; the mode change requires a fresh integrated source fingerprint and QA evidence.

Approved name/policy: exact opt-in `RADAR_SIGNUP_TURNSTILE=1`; default disabled, explicit server-provided `turnstileRequired` UI prop, no secret-dependent auto-enable and no enabled-mode fallback. Both modes retain origin/body limits, no-session pending signup, required production email delivery configuration, and combined signup/resend IP10/hour plus email3/hour/global300/hour counters before user insertion/send. Existing route IP limits remain additional protection. Enabled mode checks challenge after IP budgets and before email/global budgets. Default mode may therefore accept tokenless requests, as the user explicitly requested; that is not a CAPTCHA bypass.

Required focused regressions: production rate mode works without widget keys or token but fails without mail configuration; alternating signup/resend reaches combined IP limit after 10 total requests; rotating IPs still reach per-email/global limits; no budget failure inserts/sends; enabled mode remains fail closed for missing config/invalid challenge and does not consume email/global budget on challenge failure; UI hides widget/permits tokenless submit only in rate mode. Recheck all original email/Google/legacy security reproductions after integration. Accepted residual availability risk is quota exhaustion by distributed or targeted requests; email confirmation and strict Google subject resolution continue to prevent account access.
