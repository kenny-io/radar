## Defect found and resolved

**Q1-001 — P2 / S2,S6: same-tab confirmation reopen fails and Next history retains token.** Reproduction: open a syntactically valid `/verify-email#token=<opaque>` link; initial URL fragment is removed but Next's `__PRIVATE_NEXTJS_INTERNALS_TREE` still contains the token-bearing page URL. Refresh shows recovery as intended; reopen the same email link in the same tab (hash-only navigation) and the UI stays on recovery rather than password setup, with fragment left in URL. `EmailVerification` only reads on mount and its replaceState retains token-bearing router state. Expected every incoming confirmation fragment to be captured and scrubbed, and no token in current browser history state. E2 fixed fragment capture on mount/hashchange/popstate and scrubbed token-bearing Next router state. Independent retest passes initial link, refresh recovery, same-tab reopening, native hashchange and browser back; address/history both token-free. Complete actual-account browser suite rerun **5/5 passed**, including expiry/provider-error/replay and token-free browser storage. Synthetic-token repro is `qa/fragment-repro.mjs`; ignored evidence `fragment-before-fix.json`, `fragment-repro.json`, `fragment-reopen-final.png`. No real token in report/repro script.

Initial browser-harness assumptions were corrected before diagnosing this defect: cache header `no-store, must-revalidate` is valid; recovery CTA is a button; effect-driven notices require waiting. Initial harness evidence retained separately so assertion fixes are not mistaken for app fixes.
