## Actual automation contract

TikTok supports photo/video with explicit per-post creator privacy, interaction, disclosure and consent. YouTube requires an uploaded real video plus title, visibility and audience choices; Radar does not generate a video from a still picture.

Legacy `social.autoRun` with explicit `post:'schedule'` schedules generated X, LinkedIn and Instagram drafts for the next day. New default draft generation remains review-first. The master Autopilot coordinator iterates supported pack platforms through `canPost`; extending that helper admits Instagram, while missing TikTok/YouTube metadata is rejected by preflight and becomes an owner handoff. It must not invent TikTok privacy/consent or YouTube media/settings. A manually completed eligible post may be scheduled; a newly generated TikTok/YouTube draft must remain blocked until its per-post requirements are provided. Add integrated regressions for these cases on current-main coordinator behavior.

Thus “automation live” means Instagram can generate and publish following the owner's selected automation policy; all three can publish later from a user-configured schedule. Fully unattended creation-and-publication of new TikTok/YouTube content is not delivered by this implementation and must not be promised. TikTok's required per-post consent/audience selection and YouTube's absent video generator are real boundaries.

## Provider limits and live acceptance

TikTok currently uses sandbox credentials with target @kenny__io. [Official sandbox documentation](https://developers.tiktok.com/docs/en/add-a-sandbox) permits up to ten target accounts and excludes public-video Content Posting API access. [Direct Post guidelines](https://developers.tiktok.com/docs/en/content-sharing-guidelines) additionally restrict unaudited clients to SELF_ONLY, five publishing users per 24 hours, and require explicit per-post audience/consent. Target enrollment is separate from Login Kit authorization. Public TikTok publishing needs the appropriate production review/audit; shipping Radar does not bypass it.

Meta currently uses the selected publishing-only Unified configuration with accepted @livedhq tester access; the app is unpublished. [Meta eligibility](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/eligibility-and-troubleshooting) requires a professional account and access to the portfolio owning its Instagram assets. A tester invitation does not prove portfolio ownership or asset sharing. Actual OAuth must show the correct portfolio and assigned @livedhq asset before publication. [Unified setup](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/get-started) requires Advanced Access and Live mode for clients outside app roles. Keep the two publishing permissions and do not add ads/messages access to work around an unrelated portfolio issue.

YouTube OAuth audience is already External/In production; the new scopes remain unverified with the documented setup's unverified-user cap. Google's [seven-day refresh-token rule](https://developers.google.com/identity/protocols/oauth2#expiration) applies to External/Testing projects and therefore does not apply to the recorded current production audience. Current [videos.insert documentation](https://developers.google.com/youtube/data/reference/rest/v3/videos/insert), updated 2026-11-12, explicitly states unverified API projects are not automatically restricted to private viewing. The [current quota/audit guide](https://developers.google.com/youtube/data/guides/quota_and_compliance_audits) documents 100 uploads/day by default and an audit for quota extension. Do not repeat the obsolete blanket private-only restriction, but do not promise public posting from setup alone: verify the actual returned/uploaded resource and provider acceptance. OAuth verification, API audit and per-channel visibility restrictions are separate concerns.

Live acceptance needs the user's normal consent flows and actual correct destination accounts, durable accepted-operation/status checks, and a scheduled-send/worker-resume check. No synthetic session, imported personal login credential, fabricated provider-review demo or silently chosen destination is acceptable evidence. Record the exact content, destination, visibility and provider resource IDs for any real test publication. Use private visibility for TikTok sandbox. A public test should have concrete user-reviewed content rather than an invented marketing claim.

This makes an additive initial deployment safe without stopping the existing worker or changing the owner allowlist. Prefer updated worker first, then web if controlling order. Do not mark public provider review completed unless it is actually approved.

No schema rollback is needed. After new operations exist, avoid reverting the worker blindly: old recovery cannot resume accepted new-provider references. If a rollback is required, first stop new admissions, retain the new worker and encrypted grants/publication payload references, and inspect accepted operations before removing their recovery implementation. The owner-scoped publishing flag is a complete freeze: it also stops worker polling, so do not claim pending work will settle locally while it is off. Read provider status separately during that freeze, or selectively resume the known operations after admissions/automation are controlled. Removing developer credentials only hides new connection options and does not revoke already connected publishing tokens. Review scheduled versus sending/posted rows before any manual retry. A provider-side accepted operation may complete despite a local stop; never recreate it merely because the UI or callback failed. Prefer a forward fix or surgical feature-commit revert on current main rather than resetting unrelated production changes. Both services and flag/config state must be verified after any rollback.
