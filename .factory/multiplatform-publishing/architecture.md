# Direct Instagram, TikTok and YouTube publishing

Architecture A1; inspected 2026-11-19. Workspace `/Users/ekene/Downloads/design_handoff_radar/radar-push`, branch `kenny/signup-security`, base HEAD `f9eb6178`. The working tree contains substantial prior work; preserve it. Scope is implementation and local verification, with no release implied.

## Design

Extend the existing social account, pack, schedule and sender flow. Keep the existing Editor authorization, business-scoped OAuth states, encrypted credentials, business-scoped account lookup, row claim and unknown-outcome protections. Instagram uses professional accounts via Instagram Login and posts JPEG images or uploaded video as a reel. TikTok supports generated photo posts or uploaded video through Direct Post. YouTube requires uploaded video; a generated image cannot substitute for a video. Existing X and LinkedIn behavior remains supported.

The `social_accounts.ch`, `social_pubs.ch`, and `social_pubs.platform` columns are PostgreSQL text. The pack payload is JSONB. Extend TypeScript unions and JSON fields; no SQL migration is necessary. One account per channel per business continues to apply. Platform generation controls must expose the new platforms; creating a YouTube draft can generate text, but publishing stays blocked until a video is uploaded.

## Shared contract

- Add `instagram`, `tiktok`, and `youtube` to Platform, PostPlatform and SocialChannel. Extend `Pub.platform`, DB schema types, labels, logos, platform limits, parsers, and schedule-all validation. Stable IDs remain `s:{packId}:{platform}`.
- `SocialPost.video?: { url: string; meta: MediaMeta; durationSec?: number }` stores only a Radar-owned uploaded object. Video suppresses generated-image attachment for that send. YouTube never sends an image as video. Cap the first version at 100 MB MP4/WebM uploads (Instagram requires MP4), matching server sniffing and client validation.
- `SocialPost.publishOptions?: { title?: string; privacy?: 'public'|'private'|'unlisted'; madeForKids?: boolean; tiktok?: { privacyLevel: 'PUBLIC_TO_EVERYONE'|'MUTUAL_FOLLOW_FRIENDS'|'FOLLOWER_OF_CREATOR'|'SELF_ONLY'; allowComment: boolean; allowDuet: boolean; allowStitch: boolean; commercialContent: boolean; brandOrganic: boolean; brandedContent: boolean; consent: boolean } }`.
- Extend `Target` and preflight inputs with video and publishing options. Read actual bytes and validate type, size, object ownership and required metadata on the server. Do not trust browser MIME, URL, or stored metadata alone.
- `Media` gains `url?: string`, the provider-fetchable URL for a validated stored object, and optional duration if needed. Resolve local `/api/files/...` against configured APP_URL; reject inaccessible/private deployment URLs for URL-pull providers outside dev stubs. Do not accept arbitrary remote user URLs.
- Preserve old `upload` / `awaitMedia` / `create` adapter methods. Add optional `publish(a, { text, images: Media[], video?: Media, options?, aiMedia?, progress?(ref: string): Promise<void> }): Promise<Created>`. New providers use this path because TikTok needs post metadata before media transfer. `Created` gains optional `pending?: boolean`; `Adapter.resume?(a, ref: string): Promise<Created>` reads an existing asynchronous operation only.
- For new publish path, sender transitions to `stage='create'` before the provider can initialize a publication. Existing `payload` snapshots additionally contain options/video and an opaque `providerRef` persisted by `progress` under the current attempt key. No access tokens or bearer upload URLs belong in public workspace projections or events.

## Asynchronous safety

TikTok initialization is acceptance, not publication. Await durable `progress(publish_id)` before polling. If persistence fails after provider acceptance, surface an unknown outcome; never initiate a second post. Poll within a bounded budget (45 seconds or less). Return `pending:true` if still processing; preserve `status='sending'`, `stage='create'` and the provider reference. Refresh `claimedAt` when deliberately leaving work pending. Existing worker recovery must detect `payload.providerRef` and invoke `resume` instead of `publish` or generic retry. Resume network/rate-limit outages keep the same reference pending. Auth expiration preserves the reference for reconnect. A definitive provider FAILED result can fail the publication; PUBLISH_COMPLETE can mark it posted. Pending beyond a bounded lifetime becomes unknown and requires manual provider verification, never a new initialization.

`recoverStuck` currently rekeys after three minutes (`send.ts:28`). Keep single-call work below this threshold (100 MB video cap, 90-second YouTube PUT timeout, bounded 45-second polls) or renew the lease safely. All progress and final writes remain conditional on the attempt key. An unknown init response without a saved reference must remain unknown. Existing generic `mapCommon` treats HTTP 503 as retryable even during create; new adapters should conservatively treat ambiguous create 5xx responses as unknown.

For private TikTok posts, PUBLISH_COMPLETE may omit `publicaly_available_post_id`. A profile URL is an honest destination; do not fabricate `/video/{publish_id}`. Store the operation ID as a tracking reference if no public post ID exists. A pending post must never be marked posted, and failed UI must never say nothing was published for an unknown outcome.

## Provider details and product experience

Instagram: scopes are `instagram_business_basic` and `instagram_business_content_publish` according to the current Business Login guide. Exchange the short token for a long token. Refresh uses its current access token, so adapt the existing `canRefresh` convention (for example refresh token field can hold the access token as an internal renewal credential) without prematurely expiring it. Refresh must respect Meta's minimum token age. Publish JPEG image via `/media`, poll container status as necessary, then `/media_publish`, then read permalink best effort. Reels use `media_type=REELS` and `video_url`. Container creation cannot publish a feed post; unknown publish requests must not be reissued. The initial UI has one image per pack, so implement the existing single-image path plus reel; carousel is optional future scope unless multi-image UI is added.

TikTok: scopes `user.info.basic video.publish`; use the existing pending encrypted OAuth flow. A new authenticated, business-scoped action queries creator info to render the latest nickname, privacy options, disabled interactions, and max video duration. Privacy has no default. Interaction checkboxes start off and remain disabled where creator settings forbid them; photos show comments only. Disclosure starts off; if enabled, require own-brand or paid-partnership selection, and disallow paid partnership with SELF_ONLY privacy. Show content preview, editable caption, explicit Music Usage Confirmation consent, and Branded Content Policy consent text when applicable. Recheck available privacy/interaction permissions and duration at send time. Persist the user's explicit post options before schedule/send. Exclude TikTok from unattended auto-scheduling until a per-post choice/consent exists; never invent public privacy or consent.

TikTok photo endpoint is `/v2/post/publish/content/init/` with PHOTO + DIRECT_POST, source PULL_FROM_URL, photo_images and cover index. Video endpoint `/v2/post/publish/video/init/` can pull a video URL. Because Radar stores files server-side, official guidelines require PULL_FROM_URL rather than FILE_UPLOAD. The storage URL domain/prefix must be verified in the TikTok developer app. Photo `is_aigc` is top-level; video `is_aigc` is inside post_info. Photo caption supports 4000 UTF-16 units and title 90; video caption 2200; using a conservative 2200 shared TikTok caption limit is acceptable. Processing status comes from `/v2/post/publish/status/fetch/`; check JSON error.code even when HTTP 200. Unaudited TikTok clients are limited to private SELF_ONLY and five users per 24 hours; report provider errors honestly.

YouTube: configure a separate OAuth provider name `youtube`, requesting `youtube.upload` plus `youtube.readonly` for `channels.list(mine=true,part=snippet)`. Request offline access and preserve refresh tokens when reconnect responses omit them. Reuse configured Google credentials only as an explicit documented fallback; do not confuse the existing public-video-search API key with user upload authorization. Upload via `videos.insert` multipart media upload using title, text as description, privacy and made-for-kids metadata. Accept the returned ID only after the bytes upload succeeds; provider tracking IDs remain in private publication payloads. Actual service processing may continue after upload acceptance. Return the watch URL. Current official docs updated 2026-11-12 state unverified API projects are **not** automatically restricted to private uploads; do not repeat obsolete 2020 restrictions. Privacy must be an explicit user choice with no preselected value, and the confirmation must describe chosen visibility rather than always saying it goes live.

## Final implementation reconciliation

The video route accepts structurally validated MP4/WebM containers with a real video track (Instagram MP4 only), parses duration from actual bytes, and rejects HEIC/AVIF and magic-header-only files. Instagram generation converts its still visual to JPEG. The worker send timeout is 150 seconds, below the 180-second recovery lease. Provider status resume refreshes authentication once on a 401 and retains the same operation reference. Text, image and video changes clear TikTok consent; the UI clears it optimistically for caption edits. Automatic scheduling includes X, LinkedIn and Instagram; TikTok and YouTube remain drafts until individual required choices are supplied. YouTube multipart upload is capped at 100 MB/90 seconds and persists the accepted video ID before processing checks.

## A2 addendum: Instagram Unified Login for newly created Meta apps

This supersedes the original Instagram-onboarding choice for new Meta apps; legacy grants remain supported. Current Meta documentation says new apps cannot configure Instagram Login, while existing integrations have no announced retirement date. Unified Login uses Facebook Login for Business, a configuration ID, a Business Integration System User Access Token (SUAT), and `graph.facebook.com`. Source: [official migration guide](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/migration-guide).

### Configuration decision and evidence

PM reported creating Meta app `META_APP_ID` under owner portfolio `the configured owner portfolio`, and manually creating/selecting configuration `INSTAGRAM_CONFIG_ID`, verified in the console as Instagram Login Compatible: General, SUAT, Never expires, Instagram account asset only, `instagram_basic` and `instagram_content_publish`. Saved callback is `https://radar.thally.io/api/oauth/instagram/callback`. These are public identifiers, not secrets. Architect did not operate or independently inspect the user's browser.

The default Unified template forces messaging and proposes ad/comment access. A manual compatible configuration avoids those unused permissions. The [publishing requirements](https://developers.facebook.com/documentation/instagram-platform/content-publishing) identify the two publishing scopes; [Unified setup](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/get-started) accepts an existing configuration marked Instagram Login Compatible. PM's actual two-scope configuration settles feasibility. Do not add `business_management`: managing tokens through the optional token-management API requires it, while this Never-expiring configuration can reconnect on revocation.

### Bound OAuth and token contract

New credentials are `META_APP_ID`, `META_APP_SECRET`, `INSTAGRAM_CONFIG_ID`, and `META_GRAPH_API_VERSION` (default `v27.0`). Keep the legacy `INSTAGRAM_CLIENT_ID`, `INSTAGRAM_CLIENT_SECRET`, and `INSTAGRAM_API_VERSION` separate. Start Unified when all new credentials/configuration are present; otherwise retain the existing legacy path. Credentials stay server-only.

Start uses `https://www.facebook.com/{version}/dialog/oauth` with Meta app ID, saved config ID, exact redirect URI, `response_type=code`, CSRF state, popup display, `prompt=login`, and `override_default_response_type=true`. It must not append legacy scopes. The generated console URL includes the override, and [Facebook Login for Business](https://developers.facebook.com/documentation/facebook-login/facebook-login-for-business#business-integration-system-user-access-token-configurations) explicitly requires the override for SUAT code responses.

Save `{mode, appId, configId, apiVersion}` in server-owned OAuth state. Callback uses that state, never browser-supplied mode/config/version. Changed app ID must refuse exchange. Configuration/version changes after start must not silently redirect the in-flight authorization to another mode or graph host. Exchange with the bound version on `graph.facebook.com/{version}/oauth/access_token`, Meta app credentials, code, and exact redirect URI. See [Unified authentication](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/authentication) and [canonical code exchange](https://developers.facebook.com/documentation/facebook-login/guides/advanced/manual-flow#exchangecode).

Encrypted tokens retain `instagram: {mode:'unified', configId, clientBusinessId, apiVersion}`; no metadata means legacy Instagram Login. Adapter dispatch uses this saved provenance, not current environment settings. Never tokens have null access expiry and no refresh credential. Positive expiry responses remain expiring and require reconnect at expiry. Unified grants must never enter legacy Instagram long-token exchange/refresh or legacy `/me/permissions` revocation. Legacy token refresh should preserve saved version/provenance rather than replacing it with current defaults.

### Discovery, selection and ownership

With the SUAT, call `GET graph.facebook.com/{version}/me?fields=client_business_id`, then `GET .../me/assigned_instagram_accounts?fields=id,username`. The first `/me` ID is a system user and cannot be stored as Radar's Instagram publishing account. The client business ID is obtained from that token, never copied from the app-owner portfolio. These exact discovery calls are documented in [Get started, step 6](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/get-started#client-business-id).

Enumerate paginated accounts with a bounded page count, deduplicate IDs, and refuse invalid/repeating cursors. Rebuild pagination requests on the known Graph host instead of following arbitrary provider next URLs. Pending encrypted authorization stores the discovered list. `social.instagramAccounts` returns only names/IDs to the same business/user and Editor role; no grant metadata/tokens. Initial connection presents an unselected account picker, including a clear empty state. `social.connect` accepts only an account ID present in pending authorized identities. Reconnect retains the existing ID and scheduled posts; missing existing asset or an attempted account switch refuses and asks for reconnect or explicit disconnect. No SQL schema migration is needed.

Publishing keeps the existing container/status/publish/permalink flow, using the selected IG ID and saved Graph version/host. Existing legacy `user_id` can match the same IG account on migration; an old app-scoped fallback ID may require explicit disconnect/reconnect. Meta's migration guide distinguishes these two IDs.

### Disconnect and revocation semantics

Local disconnect deletes Radar's token copy and queued scheduled/failed pubs, preserving posted history. It does not claim to revoke the SUAT remotely. No supported programmatic revocation endpoint for this exact grant was established in this review, so a Unified revoke no-op is intentional, documented, and safer than invoking a user-token endpoint. To remove the remote grant, the client removes the app in Meta Business Settings > Integrations > Connected apps; [Facebook Login for Business token comparison](https://developers.facebook.com/documentation/facebook-login/facebook-login-for-business#comparison) documents client invalidation there. [Unified authentication](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/authentication) also documents invalidation when an app is removed or the IG asset moves portfolios. In those cases stop retrying and reconnect. This scope makes no claim that an already accepted provider-side publication can be canceled by local disconnect.
