## Approved urgent transport contract

1. Generate a cryptographically random flow UUID for each attempt before `window.open`; register receivers first. Keep popup opening synchronous with the user's click.
2. Pass flow in the same-origin start query and bind it in the existing server OAuth state's data. Derive callback flow only from that validated stored state, never an untrusted callback query. Existing state ownership, role, session, replay and encrypted-pending checks remain intact.
3. Retain direct postMessage with source/origin/provider checks and add exact flow correlation. Add a nonce-named BroadcastChannel plus a same-origin localStorage result fallback. Fallback envelopes contain only provider, flow, timestamp and the existing public `{ok,error,result}` payload, such as an opaque pending reference. Never put provider tokens, credentials or authorization codes in a browser result store.
4. Wrong provider/flow, malformed payloads, stale timestamps and duplicate messages are ignored. Keep the fallback lifetime bounded to the attempt (about ten minutes), remove its own stored result on completion and close all channels/listeners/timers. The browser message alone never authorizes account persistence: existing server `social.connect` still validates pending ownership.
5. `pop.closed` alone cannot terminate an authorization attempt. COOP can make that value true throughout consent; a two-second close grace merely reproduces the failure later. Wait for a trusted correlated result, explicit cancellation or a bounded timeout.
6. Add AbortSignal support and explicit Cancel while ConnectSocial is waiting. Modal close/unmount/retry cancels that attempt, cleans receivers and ignores a late callback. Blocked popups, denied access and timeout produce useful visible copy. Once-only completion prevents duplicate `social.connect` from several delivery paths.
7. Preserve old direct-return compatibility where necessary for pre-release pages and other providers. A missing server-bound flow must not be replaced by a callback-query value merely to make BroadcastChannel work. No new provider scopes, credentials, account bypass or global weakening of browser isolation is needed.

## Bounded retention finding and follow-up contract

The [official YouTube policies](https://developers.google.com/youtube/terms/developer-policies) require immediate programmatic revocation and Authorized Data removal within seven days for in-app revocation; periodic validity checks and removal within thirty days for externally revoked grants; refresh or deletion within thirty days for ordinary cached API data; user-requested data deletion within seven days. Historical display language is not a blanket exemption from removal after revocation. This paragraph summarizes the policy; the following is an implementation inference from Radar's actual data flow, not a legal certification.

Actual new-feature gaps: disconnect deletes account tokens and scheduled/failed pubs, but posted/sending rows retain channel-derived `acctLabel`, returned `remoteId`/`remoteUrl`, accepted `payload.providerRef`, and event props containing remoteId/url. Daily OAuth token refresh does not refresh cached channel names/handles, and definitive token failure marks the account expired without deleting those values. Pending authorizations are already pruned after one hour. General business deletion waits seven days plus worker dispatch before physical purge; do not represent it as a strict seven-day YouTube deletion guarantee without a provider-specific action.

Smallest prospective correction before asserting these new connected-YouTube lifecycle requirements are met:

- Add one provider-scoped cleanup helper for YouTube-derived identifiers/profile/status copies and encrypted grants, used by explicit YouTube disconnect, observed definitive revocation, and a user/business deletion request. Scrub returned references from matching publication payloads and outcome events as well as the account row. Avoid deleting unrelated platforms or owner-entered local drafts, uploaded source files, descriptions and scheduling choices merely because a channel is disconnected.
- Preserve a minimal Radar-owned terminal operation tombstone keyed by local SID where needed to prevent accidental automatic re-upload. It must not retain API-derived IDs, links or names. For an accepted operation whose provider reference must be removed, retain an unknown/locked terminal outcome rather than converting it into a fresh scheduled create. Do not delete remote YouTube videos or silently change their visibility.
- Reconfirm connected channel metadata/authorization on a bounded worker maintenance cadence independently of the publishing feature flag. An internal `youtube` token metadata timestamp can track a real channel-profile read without a migration; OAuth refresh `updatedAt` is not evidence that the profile was refreshed. Remove or refresh copied provider metadata before thirty days, including historical event/pub copies. Definitively revoked grants enter cleanup, transient outages do not masquerade as confirmed revocation; a hard maximum age bounds stale retained API data.
- A privacy deletion contact request must invoke that scoped cleanup in time. Revocation failures need bounded retry/observability rather than an unqualified claim that Google revoked the grant. Credential-free operation/ownership checks remain intact.

This is a connected-publishing follow-up, not authorization to erase production data or redesign Radar's older public-video-search/article embedding subsystem. The latter has its own existing metadata retention and must not be used to justify an invented assurance for the new OAuth flow. Published Google scope verification should wait for any statements about these deadlines to have concrete implemented/tested evidence; the transport hotfix can ship independently with truthful uses/disconnect copy.
