## Publication summaries

Implement one pure shared library helper so cards/filter counts agree. Derive from **projected** `post.pub` only, never `auto`, `copiedAt`, downloading, generated-media readiness or assumptions based on a pack name:

- Draft: no publication or `failed`; a failed publication additionally displays **Needs attention** and its count.
- Scheduled: `scheduled` or `sending`; additionally display **Sending** while any post is actually sending.
- Posted: `posted`.
- Mixed: a pack contains more than one of the three buckets above.

Single-bucket pack badges are Draft, Scheduled or Posted; mixed cards say Mixed and show counts such as “1 draft · 1 posted”. Filters Drafts/Scheduled/Posted include any pack containing that bucket; Mixed includes mixed packs. Thus a partially posted pack remains findable in Drafts. Filter counts follow the same membership rule and need not sum to All packs. This is tracked Radar state: a failed post is still an unpublished draft requiring attention; copied/downloaded content is not called posted. After an authorized disconnect scrubs publication records, do not invent previous receipts/status. When publishing is unavailable, use neutral **Saved** card text and hide publication-status controls (retain search), rather than assert all history was never posted.

## N8: opening a posted platform link

Additional user report: repeated View on YouTube clicks appear to do nothing after a successful post. Source diagnosis at this revision: the posted branch lives in `src/features/social/channels/PublishBox.tsx:99–104` (there is no separate PostedCard). Its current button invokes synchronous `window.open(pub.url, '_blank', 'noopener')`; no native href, alternate open affordance or failure feedback exists. `Btn` forwards the event normally (`components/ui.tsx:25`), and this path does not use Radar routing or await a server action. Consequently the source establishes a script-only opener that can fail silently in an embedded/restricted/browser popup context; it does **not** establish that Chrome actually blocked the reported click. PM owns actual browser diagnosis and should record URL presence and the observed destination before claiming a specific blocker.

A fresh successful receipt is stored by `publish/send.ts:86` with the provider URL and projected unchanged by `publish/pubs.ts:31`. `publish/youtube.ts:60` builds `https://www.youtube.com/watch?v=<encoded video id>`. In contrast, disconnect/revocation/expiry deliberately removes remote identifiers/URLs (`youtubeRetention.ts:28`) and projection independently hides stale receipt URLs. Posted status is retained with `historyExpired`/`noResend`; those records must remain local history, not become a second send or reconstructed link. Reconnection does not restore scrubbed provider data.

Smallest UI fix, owned by the same UI engineer: extend ownership to **`src/features/social/channels/PublishBox.tsx` only**, replace the live posted View control with a native `<a className="btn btn-secondary btn-block" href={...} target="_blank" rel="noopener noreferrer">` using existing LogoLabel/button appearance. Do not change global Btn or the router, call `window.open`, prevent the anchor’s default event, perform an API call before opening, or add popup-retry logic. Accept only an absolute HTTP(S) URL for navigation; unsupported/malformed URLs have the same unavailable treatment. For YouTube `historyExpired` always suppresses the exact-video link even if a stale URL were accidentally present in client memory.

If no usable projected URL exists, render plain explanatory text, **not an inert View button**: use the existing connection-details-removed explanation for historyExpired; otherwise “The post link is unavailable. Check <platform> for this post.” Keep the posted timestamp and existing copy/download actions. An optional separately labeled Open YouTube homepage link may use a constant public homepage, never be presented as the removed video link. Do not derive a receipt from the R2 upload URL, a previous recording, a known video ID, the pack ID, or a newly connected account. No backend retention/projection modification is required.

## Separate follow-on: duplicate as draft (not N1 implementation)

PM explicitly deferred a general cloning feature; D2 uses the reviewed one-shot operation for the immediate recording. A future smallest product flow is **Duplicate as draft** for the current selected platform in PackView, available to Editor/Owner even when its original is posted. Input `{packId, platform, token}` through an ordinary authorized `social.duplicate` action; server derives business from ActCtx, never client tenant/URLs/generation IDs. Return `{packId}` and open the saved new draft. A client request token provides idempotency: repeated request returns the same newly created snapshot without overwriting later edits.

Use an explicit whitelist projection, fresh ID/date/name, `auto:false`, one selected post/platform and a transaction with owned source/asset locks. Copy text, source/headline/grounding/voice, stable visual attachment and its **original** immutable generatedMedia provenance; clear publication/receipts/schedules/approval/account/default/automation refs, copy marks, counters and pending-generation state. Clear per-post visibility/audience/TikTok consent so the owner chooses again; optional title content can remain. Do not spread operational fields or reset the original post/social_pubs. Pending/ambiguous replacement refuses rather than copying a disputed intent. A stable old attachment must be labeled/copied with actual style, not desired replacement style.

For generated media validate owned ready generation, exact attached output, sourceHash/checkpoint binding and supported readiness; preserve original paid generation ID and notes access, no new AI/TTS/render/upload/job or invented generation row. Existing same-business pack references protect shared generated assets/narration from `collectMediaCache`; verify with a GC regression. Copying is a snapshot reuse operation, not fresh planning: never assert that a changed live URL/business profile was newly reviewed, fabricate a new source/cap binding, or perform network fetches under database locks. Any future regeneration uses ordinary fresh source/cap fences. Manual legacy media needs its own owned-storage/readiness case; do not call it AI-generated. This follow-on requires tenant/isolation, whitelist/reset, idempotency/concurrency, preflight/notes/retention and zero-paid-call tests before release. No generic duplicate implementation is authorized by this N1 design.
