## Retry recipient boundary: required narrow guard

QA found a concrete stale-recipient path: handoff reads today's owner email, but main `sendMail` subsequently overwrites it with an earlier persisted outbox row.to when retrying the same key. After a failed/ambiguous attempt, changing the owner's mailbox can therefore send private prepared drafts to the old address. Current handoff also selects guest/email but not emailVerifiedAt.

1. `deliverHandoff` must require a current non-guest, email-verified owner with the same persisted ownerId, plus the current activation/access checks. Unverified/missing/changed owner produces no provider call and no new mail key. Do not treat ordinary registration as mailbox verification.
2. In the idempotent general helper, retain the caller's requested current recipient separately. For an unsent existing outbox row, require exact stored row.to===requested recipient BEFORE replacing arguments with persisted envelope or performing a provider POST. A mismatch is a permanent delivery safety failure (`RadarError` code `mail_recipient_changed` is a suitable exact contract), not a retry with changed body/address/key. Previously sent/logged rows may retain their no-provider-call short circuit; this acknowledges past acceptance rather than sending new private content.
3. Handoff surfaces a controlled owner-visible lastError and converts this mismatch into `PermanentJobError`/terminal state rather than repeatedly POSTing or pretending delivery succeeded. Preserve the original outbox row, body and provider key for investigation. Never auto-rekey to the new address after an ambiguous old-address attempt. No email address/body/provider response should enter error logs.

Same-address retries remain immutable and idempotent. An owner/recipient change after an actual successful historical send cannot recall that send; it must still cause no new POST. QA should use mocked transports and a failed persisted row to prove this distinction.
