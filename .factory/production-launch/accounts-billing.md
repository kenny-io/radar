## Implemented fixes

- Public signup/signin previously had no abuse throttles, unbounded strings and unrestricted JSON reads. Both now reject foreign browser origins, cap streamed JSON at 8KB, bound name/email/password/return-path lengths, and throttle through the existing shared Postgres limiter before expensive work. Signup: 10 attempts/IP/hour; signin: 30/IP/15min plus 10/normalized email/15min. Email limiter keys contain SHA256, not raw addresses. API clients without Origin remain supported; cross-site Fetch Metadata or a conflicting Origin is refused.
- New passwords above **72 UTF-8 bytes** are rejected explicitly because bcrypt otherwise silently ignores the remaining bytes; multibyte cases tested. New signup names ≤200 characters, emails ≤320, passwords ≤256 characters subject to the byte limit. Signin accepts legacy passwords up to 1024 characters, retaining existing accounts whose earlier passwords exceeded 72 bytes. Signup uses the unique email constraint to resolve simultaneous submissions as one success and one helpful 409. Input email whitespace is normalized consistently.
- Google sign-in previously stored state without browser binding or an expiry check, with select/delete consumption. State now has a 10-minute HttpOnly/SameSite=Lax cookie (Secure in production), must match its initiating browser, and is consumed by one provider/age-qualified DELETE RETURNING. Google-start requests are throttled (30/IP/15min). Token exchange has a 15-second timeout; malformed/network errors return the existing retry screen; audience, verified email, issuer, subject and expiration are checked. Concurrent account creation reuses a verified matching account rather than producing a duplicate-insert 500. Existing Google claim tests now supply the required initiating-browser state cookie.
- **Reproduced pricing defect:** a failed $1 balance credit was swallowed, marking the payment webhook processed and potentially losing the promised first-month credit. Activation now fails its transaction when the credit fails, leaving the event retryable. Retries adopt the already-created subscription and preserve the credit idempotency key. Regression confirms one charge, subscription, credit, trial event and draft commit.
- Stripe HTTP attempts previously had no timeout while billing held a database transaction/lock. Each request and response body now has a 15-second cancellation deadline; bounded existing network retries preserve the original payment key. A simulated stalled transport regression proves cancellation, retry bounds and unchanged idempotency key.
- Existing signup layout now includes linked Terms agreement and Privacy Policy acknowledgment (signup/Google only); error hints announce failures. Trial fine print now discloses the $1 credit, **$49 first monthly bill, then $50/month**, and cancellation in Billing before trial expiry to avoid monthly subscription charges. Existing price/trial constants and business policy preserved.

## Final availability follow-up — E4

Publishing response deadlines now remain attached after successful response headers while callers consume text/JSON/binary bodies. Real local HTTP regressions reproduced the prior lost deadline, then passed with the complete request/body deadline. After a successful write's headers, a failed body is classified as nonretryable `ambiguous-write`: **“The platform may have saved this post. Check your blog before trying again.”** The HTTP helper adds no retry, and the existing publisher queue does not resubmit this class. Generic pre-header transport failures and existing malformed-JSON write responses can still be ambiguous; this is not an exactly-once publishing guarantee.

The unauthenticated billing webhook refuses missing configuration/signatures before reading the body, enforces a 1MiB raw-body cap for declared or unknown lengths, cancels on overflow with 413, and preserves valid raw UTF-8 signature/replay behavior. Four webhook-boundary tests and four actual stalled-body HTTP tests pass. Combined affected publishing/actions/auth/billing developer suite: **415 passed, 65 external-harness skips**; typecheck and whitespace checks passed. ## Actual hosted-portal cancellation shape — E5

Real QA found the pinned Dahlia portal returned `status: trialing`, `cancel_at: 1793911362`, `cancel_at_period_end: false`, `canceled_at: 1793652415`, with item `current_period_end: 1793911362`. The old adapter persisted a false warning despite a scheduled cancellation. Regressions reproduced the defect before the fix.

The Stripe adapter now normalizes a scheduled-at-period-end flag when **`cancel_at` exactly matches the real item period end**, or the legacy explicit boolean is true. It never substitutes cancellation dates for billing dates. `canceled_at` is historical request time and does not set the flag; canceled, paused and incomplete-expired subscriptions clear it. Arbitrary dashboard custom-date cancellations that differ from the billing period remain outside the supported portal/UI contract; the adapter leaves this period-end flag false and preserves the actual billing date. Radar's configured portal offers cancellation at period end. No schema or shared-type migration was introduced.

Seven actual-shaped adapter cases cover explicit flags, the observed portal response, custom differing dates, historical `canceled_at` and terminal states. A DB-backed test runs the actual adapter response through webhook synchronization and verifies persisted overview, replay, schedule removal and terminal clearing.
